# Switchyardの技術解説

[English](walkthrough.md) | [日本語](walkthrough.ja.md)

Switchyardは架空のクリエイティブ素材を、検証、プロバイダーレビュー、人の承認、ローカル納品の順に処理します。AtlasとCedarは決められたテスト応答を返すフィクスチャであり、実モデルを呼び出しません。

## 処理の流れ

| コンポーネント         | 役割                                                                                                           |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| `src/core/contract.ts` | 入力、レビュー、承認、納品、実行記録のスキーマを定義する。レビュー指摘は素材IDを通じて既知の素材に結び付く。   |
| `src/core/workflow.ts` | サーバー側で状態遷移と承認を検証する。承認は入力の版とダイジェストに対応し、入力が変わると無効になる。         |
| `src/core/gateway.ts`  | 試行回数と期限を制限する。タイムアウト、不正応答、利用不可では切り替え可能だが、明示的な拒否では停止する。     |
| `src/core/store.ts`    | チェックポイントとコマンド記録を保存する。更新番号で古い更新を拒否し、コマンド記録でローカル操作の重複を防ぐ。 |
| `src/core/delivery.ts` | 承認後にローカルファイルを作成し、ダウンロード前にSHA-256ハッシュを検証する。                                  |

Reactの画面は実行一覧、レビュー表示、新規作成ダイアログで構成します。UIの操作可否はサーバーの状態を反映し、サーバーは各遷移を独立して検証します。

## 設計判断

| 判断                               | 理由と保証の範囲                                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| アプリと検査ツールを分離する       | Switchyardは処理と人の判断を担当し、FieldcheckはJSONL出力契約を独立して検査する。ゲートウェイは利用者が1つなのでアプリ内に置く。                                   |
| 検証済みレビューの後に人が承認する | 形式と素材への参照が正しくても、内容の正しさや納品の意図は証明されない。承認を入力の版とダイジェストに結び付ける。                                                 |
| 中断後は明示的に再試行する         | プロセス停止で中断したレビューは、保存済み入力に対する新しいレビュー操作で再試行する。保存済みの承認は納品まで再開できる。                                         |
| コマンドの重複をローカルで抑える   | コマンド記録は状態遷移を重複排除する。プロバイダー呼び出しは再起動後に繰り返され得る。外部納品には相手側の冪等性やトランザクショナル・アウトボックスが必要になる。 |

## 再現できる検証

[READMEのデモ](../README.ja.md#90秒で試せるデモ)では、切り替え、承認、納品、入力変更による承認無効化、障害からの復旧を確認できます。`tests/restart.test.ts` は、レビュー中のNodeプロセスを実際に停止し、新しいプロセスで保存済み入力を再試行します。承認後にもう一度停止し、再起動後に1回納品します。検証範囲はプロセスの中断であり、停電や分散環境の復旧ではありません。存在しない素材IDの拒否、プロバイダーの拒否・中断の動作もテスト対象です。結果は[検証記録](verification.md)にまとめています。

素材の内容が変わると、素材のハッシュと入力全体のダイジェストが変わります。このダイジェストは承認の条件なので、古い入力への承認で変更後の素材を納品することはできません。

## 拡張時の境界

別のプロバイダーを加える場合は、`Provider` インターフェースの拒否と中断の動作を維持する必要があります。ファイル保存をSQLiteやPostgresに置き換える場合は、更新番号、コマンドの重複排除、入力への承認の対応を維持する必要があります。GCPで動かす場合は、認証、トランザクション付き状態保存、永続キューとワーカー、素材の保管、運用監視も必要です。これらの拡張は未実装・未検証です。

フィクスチャの処理時間はローカルコードの実行時間であり、実モデルの推論速度や品質ではありません。詳しい設計は[設計とトレードオフ](architecture.md)に記載しています。
